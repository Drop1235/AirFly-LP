# リリース前テスト仕様書（第2段階・セキュリティ修正の確認）2026-10-10

対象: AirFly LP（`Drop1235/AirFly-LP`）
目的: 第2段階で確定した脆弱性 V1〜V9 の **修正確認** と、修正による **正常系の非回帰（デグレ防止）** を、本番に影響を与えずに検証する。
前提: 本番（Netlify / Firebase / GAS / Stripe）には直接攻撃テストを行わない。**Firestore エミュレータ＋Stripe テストモード**で確認する。本番で行うのは「正常系の通し」と「設定確認」のみ。

関連: 脆弱性の詳細は `docs/release/2026-10-10-stage2-security-report.md`。

---

## 0. テスト環境

| 区分 | 使うもの |
|---|---|
| Firestore / Auth | ローカルエミュレータ（`firebase emulators:start --only firestore,auth`、`demo-` プロジェクト） |
| Stripe | **テストモードの鍵**（`sk_test_` / `whsec_`）と Stripe CLI の `stripe listen` / `stripe trigger` |
| GAS | テスト用スプレッドシート＋テスト用デプロイ（本番台帳とは別物）。または GAS 相当のモック受け口 |
| Netlify Functions | `netlify dev`（ローカル）で関数を起動し、`curl` で直接叩く |

> ⚠️ 本番の Stripe 鍵（`sk_live_`）や本番 GAS URL、本番 Firestore プロジェクトIDは**使わない**。攻撃系のテスト（T1〜T9 の「攻撃」ステップ）は必ずローカル／テストモードで行う。

判定記号: ✅ = 期待どおり（合格） / ❌ = 期待どおりでない（不合格・リリース不可）

## A. セキュリティ修正の確認（攻撃が塞がれていること）

### T1 — V1：client 由来 `projectId` の遮断
**ねらい**: 攻撃者が自分のプロジェクトを指して割引を得られないこと。

| # | 手順 | 期待結果 |
|---|---|---|
| T1-1 | `netlify dev` で `create-checkout-session` を起動。`curl` で正常な注文（クーポンなし）を POST | ✅ 正価の Checkout セッションURLが返る |
| T1-2 | ボディに `"projectId":"demo-attacker"`, `"coupon_code":"ANYCODE"` を付けて POST（攻撃者プロジェクトに 99%OFF クーポンを置いた想定） | ✅ **割引が適用されない**（正価のまま）。または 400。❌ 割引が乗ったら不合格 |
| T1-3 | 関数ログに、クライアント `projectId` を参照していないことを確認（コードレビュー） | ✅ `projectId` は `JSON.parse(event.body)` から取得していない |

### T2 — V2：1回限りクーポンの消費がサーバー側
**ねらい**: 同じ単回クーポンを2回使えないこと。消費がブラウザに依存しないこと。

| # | 手順 | 期待結果 |
|---|---|---|
| T2-1 | エミュレータに `coupons/TEST1`（`isUsed:false, isUnlimited:false, discountRate:20`）を作成 | — |
| T2-2 | `create-checkout-session` を `coupon_code:"TEST1"` で**直接** POST（ブラウザを経由しない） | ✅ 20%OFF が適用され、**同時に `coupons/TEST1.isUsed` が true になる** |
| T2-3 | もう一度同じ POST | ✅ 割引が適用されない（既に使用済み）。❌ また割引が乗ったら不合格 |
| T2-4 | `isUnlimited:true` のクーポンで2回 POST | ✅ どちらも割引適用（無制限は消費しない） |
| T2-5 | 期限切れ（`expiresAt` が昨日）のクーポンで POST | ✅ 割引なし |
